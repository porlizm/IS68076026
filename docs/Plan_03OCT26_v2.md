## 0. สรุปหนึ่งหน้า

PoC ใน Demo ตอบสิ่งที่ระบบเต็มยังไม่เคยถูกทดสอบ คือ **คะแนนแยกอาชีพได้จริงไหม** และคำตอบคือ "ไม่ได้ ถ้าใช้ R อย่างเดียว" เพราะข้อกำหนด Top-30 ของ 20 อาชีพไอทีซ้ำกันมาก และโมเดลไม่แยกว่าใครเป็นผู้ลงมือทำ สิ่งที่แก้ใน Demo (actor, จำกัด quote ซ้ำ, idf, Role-Fit) จึงไม่ใช่แค่เรื่องหน้าตาของ Demo แต่กระทบ **สถานะรายข้อ** ซึ่งเป็นตัวที่คำถามการวิจัยข้อ 1 วัดโดยตรง

ข้อเสนอหลักมี 5 ข้อ เรียงตามผลต่อคุณภาพงานวิจัย

1. **ย้ายกฎที่พิสูจน์แล้วใน Demo เข้าระบบเต็ม (engine 2.1)** เฉพาะส่วนที่เปลี่ยนสถานะ (actor, จำกัด quote ซ้ำ) และส่วนที่ต้องใช้รายงานผล (token, ตราประทับรุ่น) · Role-Fit/idf เป็นตัวชี้วัดเสริมในรายงานผู้เรียน ไม่ใช่ตัวชี้วัดของ RQ
2. **ให้คู่มือให้รหัส (Coding Manual) ใช้นิยามเดียวกับกฎของระบบ** โดยเฉพาะ "ทำเอง vs กำกับ" ถ้าไม่ทำ ชุดคำตอบอ้างอิงกับระบบจะวัดคนละสิ่ง และ Macro-F1 จะต่ำเพราะนิยาม ไม่ใช่เพราะระบบ
3. **เพิ่มการวิเคราะห์องค์ประกอบภายในรอบเดียวกัน (component analysis) เป็นผลเสริมเชิงพรรณนา** ใช้ log ที่ระบบเก็บอยู่แล้ว (ผลของแต่ละโมเดล · R3 คำซ้ำอย่างเดียว · ไม่มีกฎ) เทียบกับชุดคำตอบอ้างอิงเดียวกัน ไม่ต้องเก็บข้อมูลเพิ่ม และทำให้ชื่อเรื่อง "Reducing Hallucination" มีหลักฐานรองรับ (ตอนนี้ข้อจำกัดข้อ 4 ใน 3.9 ยอมรับว่าตอบไม่ได้) 🎓
4. **ปิดช่องความตรงของคะแนนก่อนเก็บข้อมูล** รัน known-group / style / stability (DEC-57) กับระบบเต็มบนบริการจริง และใช้ผลเป็นเกณฑ์ผ่านก่อน freeze
5. **เดินเส้นทางวิกฤต (สอบ → จริยธรรม → นำร่อง) ขนานกับงานระบบ** ไม่ให้งานระบบดึงเวลาจากการยื่นจริยธรรม

### S5 · ความสามารถในการทำซ้ำและการ freeze · ต้องทำ

1. ทุกแถวในแท็บ `runs` บันทึก `wf_version · build_id · engine_version · prompt ids · model ids ที่ตอบกลับจริง · rules_version · data sha`
2. ก่อนนำร่อง: freeze ข้อมูล (manifest frozen=true) + tag `freeze-v1.0` + ปิดการแก้ workflow ระหว่างเก็บข้อมูล
